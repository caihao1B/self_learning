第 05 章 ROS 通信与生命周期

ROS 2 为多个程序提供通信约定。它不替你判断传感器是否可信，也不保证动作完成后车已经停止。本章把 topic、service、action 和生命周期放进同一个任务里理解，避免把“发出一条消息”误认为“执行了一个行为”。

节点、消息与话题

节点是 ROS 图中的参与者，可以发布和订阅消息。topic 是具名数据流，例如点云、轮速、工具状态；消息类型规定字段结构。订阅者收到的数据仍需要检查时间、坐标系和有效性。一个空点云和一个障碍很少的点云，都可能有相同消息类型。

sensor_msgs/PointCloud2 用字段定义和字节数组表达点云，sensor_msgs/Imu 表达角速度、线加速度、姿态和协方差，nav_msgs/Odometry 表达位姿与速度。消息名中的 Odometry 不要求输入只能来自车轮。项目的 JSON 状态 topic 使用 std_msgs/String 承载序列化对象，字段语义还需读发布端与订阅端约定。

service 与 action

service 适合一次请求对应一次响应，例如读取配置或申请重置。服务器完成处理后返回；它不适合表示持续几分钟、需要进度与取消的任务。

action 分为目标、反馈和结果，还支持取消请求。导航客户端首先等待服务器，发送目标后收到是否接受，之后接收反馈，最终获得结果。取消也需要响应；发送取消请求不等于服务器已经停止。

工具 ToolTask.action 用两个 --- 将定义分成 Goal、Result、Feedback。Goal 包含工作身份、请求量、目标及版本等；Result 说明成功与确认量、残余和停止状态；Feedback 描述执行过程。具体字段以本章固定定义为准，不能拿新版本 action 与旧二进制混用。

main 创建节点、ActionClient 与订阅，将状态保存到 st。lambda 的 k=key 固定循环键；事件日志把阶段和仿真时间串起来。ActionClient 的类型决定协议，任务函数再决定什么时候发送或取消。

读接口时先找单位和身份：同一 work_key 的重试应指向同一原工作义务；request_id 等传输身份与工作身份不能随意合并。若取消后工具反馈不确定，任务不能立即给同一点重新发满额请求，否则可能重复喷洒。

回调为何需要 executor

ROS 数据到达通信层后，需要 executor 调度回调。Python 中 rclpy.spin_once(node, timeout_sec=...) 处理一次可执行工作；Future 完成标志也依赖回调推进。若任务在循环中只调用 time.sleep，可能让消息排队而状态永远不更新。

单线程执行器容易理解，但一个回调耗时过长会拖住其它回调。多线程执行器提高并发能力，也引入共享状态同步要求。选择哪种要看回调成本和数据所有权，不能简单认为线程越多越好。

QoS 为什么决定能否收到消息

QoS 是发布与订阅的交付约定。Reliability 控制可靠或尽力而为；History/Depth 控制保留多少；Durability 决定晚加入者能否收到保留样本。高频传感器常用 sensor-data 风格的 best effort、小队列，以新鲜度优先。状态与动作结果可能需要不同策略。

可靠订阅不一定能匹配 best-effort 发布；旧地图需要保留样本也不意味着所有高频点云都应 transient local。队列变大可以减少短时丢失，却可能让系统消费过期数据。通信可靠性、时效性和应用有效性是三种不同属性。

生命周期怎样影响 Nav2

生命周期节点可经历 unconfigured、inactive、active 等状态。configure 通常创建资源，activate 允许对外工作。进程存在、节点能被列出，并不意味着控制器已经 active。Lifecycle manager 负责按依赖管理这些状态。

因此“找不到 action server”可能来自服务未启动、生命周期未激活、命名空间不对、domain 不一致或初始化失败，不能直接归因于导航算法差。

只读观察命令

以下命令只在已有当前任务运行时有意义；本教材检查不会自动启动它。

cd /home/ceihao/robot_project
source optimization_v2/env.sh
ros2 node list
ros2 topic list -t
ros2 action list -t
ros2 service list -t

list 列出图中的对象，-t 附带类型。先从输出确定真实名称，再检查具体话题：

ros2 topic info /clock --verbose
timeout 8s ros2 topic echo /clock --once

timeout 8s 限制观察命令的现实等待，超时通常返回 124；这不等于仿真故障已被诊断。--once 收到一条后退出；一条消息不能证明持续频率。对于传感器 best-effort 发布，可按 ros2 topic echo --help 选择匹配 QoS，避免因默认订阅不兼容误判数据缺失。

离线动作协议练习

执行 python3 examples/l02/labs.py 05。它不是 ROS 客户端，而是逐事件演示 accepted、terminal、stopped 三个独立状态。取消请求到来时 terminal 仍为空；取消确认后仍需实测停止。这样的状态拆分正是复杂任务可靠收尾的基础。

def lab05():
    """Teaching action protocol: acceptance, feedback and result are distinct."""
    events = [('GOAL_SENT', 0), ('ACCEPTED', 1), ('FEEDBACK', 2),
              ('CANCEL_REQUEST', 3), ('CANCELED', 4), ('STOP_CONFIRMED', 5)]
    accepted = False; terminal = None; stopped = False
    trace = []
    for event, t in events:
        if event == 'ACCEPTED': accepted = True
        if event == 'CANCELED': terminal = event
        if event == 'STOP_CONFIRMED': stopped = True
        trace.append(dict(t=t,event=event,accepted=accepted,terminal=terminal,stopped=stopped))
    assert trace[3]['terminal'] is None and trace[-1]['stopped']
    return dict(kind='synthetic protocol, not ROS action test', trace=trace)

常见故障与自测

话题存在却没有数据：看发布者数量、QoS、时钟、任务阶段和消息频率。action 接受后一直不结束：检查回调是否推进、控制器是否 active、是否被门控、任务是否还在等待可信定位。多个同名节点：检查是否误开第二个任务，以及运行器会话锁是否生效。

问：为什么不使用 topic 发一个“开始喷洒”就结束？答：topic 本身不包含长任务目标、反馈、最终结果和取消协议；可以额外设计这些，但 action 已提供合适的通信骨架，业务仍要自行检查反馈。

练习：把“请求取消”“服务器确认取消”“车体速度接近零”“工具确认停止”写成四行。指出其中哪两行来自协议、哪两行来自观测。能区分它们后进入坐标与时间章。
